## 1. Валидатор схемы

Реализован `validate_plan(plan: Plan) -> list[str]` в `orchestrator.py`.
Встроен в `run_pwc()` сразу после `planner(...)`: при наличии ошибок вызывается
`planner(question, feedback=...)`, а если план остаётся невалидным — система
честно отказывается исполнять выдуманные инструменты.

```python
VALID_TOOLS = {"get_fx_rate", "get_key_rate", "get_inflation", "calculate"}

def validate_plan(plan: Plan) -> list[str]:
    """Вернуть список ошибок плана (пустой — всё ок)."""
    errors: list[str] = []
    for sq in plan.subquestions:
        unknown = sorted(set(sq.expected_tools) - VALID_TOOLS)
        if unknown:
            errors.append(f"sq{sq.id}:unknown_tools:{','.join(unknown)}")
        if not sq.expected_tools and sq.question.strip():
            errors.append(f"sq{sq.id}:empty_expected_tools")
        if sq.id in sq.depends_on:
            errors.append(f"sq{sq.id}:self_dependency")
    ...
    return errors
```

Примеры пойманных планов:

```
# Q3 "накопленная инфляция" — планировщик без валидатора выдумывает:
sq1:unknown_tools:get_cumulative_inflation

# Q4 "средняя ключевая ставка" — планировщик выдумывает:
sq1:unknown_tools:get_average_key_rate

# Структурные ошибки (синтетический тест):
sq1:self_dependency
duplicate_subquestion_id:1
sq3:missing_dependencies:[9]
dependency_error:цикл в depends_on: [1]
```

## 2. Параллельность

Плоская сортировка заменена на `_topological_levels(...)`, которая возвращает
список уровней. Независимые подвопросы одного уровня выполняются параллельно
через `execute_level(...)` с `ThreadPoolExecutor(max_workers=4)`.

| Вопрос | Последовательно | Параллельно | Ускорение |
|---|---:|---:|---:|
| Q1 (USD, 3 подвопроса) | 84.1 с | 54.4 с | **1.55×** |
| Q5-bonus (6 валютных подвопросов) | 187.0 с | — | не сошёлся¹ |

¹ Параллельный прогон Q5 не получил вердикт `accept` за 3 итерации — критик
отклонял план три раза подряд. Последовательный прогон того же вопроса завершился
успешно за 187 с. Реальное ускорение зафиксировано на Q1: два независимых
fx-подвопроса уровня 1 выполняются одновременно.

## 3. Замер критики

Критик прогнан на 5 заведомо битых наборах ответов (N=10 на каждую температуру,
ошибок API: 0).

| Битый кейс | T=0.0, ложных принятий | T=0.7, ложных принятий |
|---|:---:|:---:|
| арифметика без calculate | 1/10 | 0/10 |
| выдуманное число | 2/10 | 0/10 |
| несогласованные данные | 2/10 | 2/10 |
| пропущен подвопрос | 0/10 | 0/10 |
| ответ с ошибкой инструмента | 0/10 | 0/10 |
| **Итого** | **5/50** | **2/50** |

T=0.0 пропустил 5 битых ответов, T=0.7 — только 2. Гипотеза «шум лечит
зеркальное соглашение» **подтвердилась**: при нулевой температуре критик
чаще соглашается с планировщиком, при T=0.7 добавляется случайность, которая
позволяет замечать ошибки.

## 5. Вывод

PWC оправдан, когда вопрос естественно раскладывается на несколько независимых
фактических подвопросов: курсы нескольких валют, ставка + инфляция + арифметика,
сравнение двух периодов. В таких задачах план делает структуру явной, параллельность
экономит время (до 1.5×), а критик ловит пропущенный `calculate`.

Валидатор схемы — обязательный элемент: без него планировщик выдумывает
несуществующие инструменты (`get_cumulative_inflation`, `get_average_key_rate`),
и исполнитель молча возвращает ошибку. С валидатором система либо перепланирует
корректно, либо честно отказывается.

Одиночный агент лучше оставить для коротких одношаговых вопросов (текущая ставка,
курс одной валюты) и для задач на границе инструментов — например, Q2 («реальная
ставка по последнему месяцу») одиночный агент решает гибче, чем PWC с жёстким
валидатором: он сам выбирает последний доступный месяц из контекста, не требуя
специального инструмента.
