# Основы RAG для внутренних помощников

Источник темы: открытые материалы LangChain и обзорные статьи о retrieval augmented generation. Текст ниже является авторским учебным конспектом для домашнего задания.

RAG, или retrieval augmented generation, используют тогда, когда языковой модели нужно отвечать не только из параметров, но и из конкретного корпуса документов. В классической схеме пользователь задает вопрос, система ищет релевантные фрагменты, добавляет их в промпт и просит модель сформулировать ответ только по найденному контексту. Такой подход особенно полезен для внутренних помощников компании: база знаний меняется быстрее, чем обновляется модель, а в ответе часто нужны ссылки на конкретные регламенты, инструкции или обсуждения.

Главное преимущество RAG состоит не в том, что модель становится всезнающей, а в том, что ее ответ получает опору на проверяемые источники. Если в контексте есть цитата из документа, можно показать пользователю, откуда взялся вывод. Это снижает риск галлюцинаций, потому что модель меньше додумывает детали. Однако риск не исчезает полностью. Если ретривер нашел неправильный фрагмент, если вопрос сформулирован слишком широко или если модель игнорирует ограничение "отвечай только по контексту", итоговый ответ все равно может быть неверным.

Обычно RAG-пайплайн состоит из нескольких этапов. Сначала документы очищают от служебного шума, разметки, повторяющихся футеров и пустых строк. Затем их режут на чанки. После этого для каждого чанка считают представление: dense embedding, sparse tokens для BM25 или оба варианта сразу. На этапе запроса вопрос пользователя преобразуется в такой же формат, выполняется поиск top-k, и найденные куски передаются в генератор. Для учебной работы достаточно оценить именно retrieval, потому что качество ответа модели зависит от того, попал ли нужный источник в top-5.

Чанкинг сильно влияет на результат. Если куски слишком длинные, один чанк может содержать много разных тем, и совпадения по словам будут размываться. Если куски слишком короткие, важная мысль может разорваться между соседними фрагментами. Поэтому fixed-size разбиение удобно как базовая линия, но оно не учитывает структуру текста. RecursiveCharacterTextSplitter пытается сначала делить по заголовкам и абзацам, потом по предложениям и только потом по пробелам. Это часто дает более читаемые чанки.

В корпоративной базе знаний RAG особенно полезен для трех задач. Первая задача — быстрый поиск по инструкциям и регламентам. Вторая — объяснение сложных решений с цитатами из источников. Третья — помощь аналитикам, когда нужно собрать ответ из нескольких документов. Последний случай называют multi-hop: например, один документ описывает архитектуру индекса, второй — метрику качества, а ответ требует связать оба факта.

Но у RAG есть ограничения. Система плохо работает, если в корпусе нет нужного документа, если документ устарел, если вопрос требует вычислений, которых нет в тексте, или если пользователь использует синонимы, а поиск настроен только на точные слова. Поэтому полезно строить gold-набор: несколько вопросов, для которых заранее известно, какие источники должны попасть в выдачу. Такой набор помогает сравнивать стратегии чанкинга без субъективного впечатления.

В этом домашнем задании RAG оценивается через hit-rate@5. Для каждого вопроса берется пять найденных чанков. Если среди них есть хотя бы один чанк из нужного документа, вопрос считается найденным частично или полностью. Для multi-hop вопросов, где нужно несколько источников, оценка считается как доля найденных источников. Например, если нужно два документа, а найден один, score равен 0.5.
